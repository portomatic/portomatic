iOS on Linux: MVP Layers

An iOS engineer supplies a repository. The service builds and runs it.

These are guesses, not measurements. They assume 3–5 full-time engineers experienced in kernels, binary compatibility, graphics, and iOS internals. Hover citations for offline evidence.

The answer

Build a headless CoreSimulator environment over a narrow Darwin compatibility layer. Keep the real ARM64 Simulator runtime and app frameworks. Replace only the host contracts reached by one pinned workload.

No Linux port of the app exists. The engineer does not rewrite SwiftUI, replace UIKit, add a Linux target, or maintain platform-specific seams.

Do not put Simulator.app, AppKit, or a complete simctl clone on the critical path. The project has already measured a direct IOSurface pixel boundary and a direct HID-to-Mach input path.[2][3]

The input contract

The only product input is the existing iOS repository. Therefore the service must:

  1. discover its workspace, project, schemes, targets, and build configuration;
  2. resolve SwiftPM, CocoaPods, and checked-in dependencies;
  3. run Swift, Objective-C, C/C++, linker, macro/plugin, script, asset, storyboard, and bundle build phases;
  4. produce an ARM64 iOS Simulator .app;
  5. install, launch, observe, interact with, and reset it.

A full-system iOS VM solves only step 5. It does not build source. The build lane is mandatory for every runtime architecture. xtool proves a useful but narrower starting point—building SwiftPM iOS apps on Linux—not arbitrary Xcode workspaces.[8]

What “MVP” means

First interactive app
One unmodified pinned repository builds on Linux; its app produces a stable frame; one touch changes app state and the next frame.
Agent MVP
Representative production repositories build without source edits, install, launch, render, accept touch and text, use files and networking, emit logs and crashes, and warm-reset reliably.
I/O complete
Agent MVP plus sound output, injected microphone input, an accessibility/semantic tree, and at least 34 useful concurrent sessions on a $1/hour host.

“Runs Hello World” is a loader milestone. It is not the product.

The recommended layer

One session

This preserves the behaviorally valuable middle: real UIKit, SwiftUI, Foundation, the Objective-C and Swift runtimes, SpringBoard/backboardd, and Simulator services. It avoids modeling an iPhone’s boot ROM, SEP, interrupt controller, storage controller, GPU, sensors, and baseband.

Kakehashi already demonstrates the correct ISA relationship—ARM64 Darwin binaries executing natively on Linux AArch64—but explicitly does not claim GUI or the full macOS app stack.[4] Darling supplies the complementary design: Mach-O loading, a userspace Mach state owner, syscall translation, and framework/service replacements.[5]

The first four weeks

The first month should try to kill the recommended architecture cheaply.

  1. Week 1 — process boundary. Run the same tiny Darwin ARM64 binary on macOS and Linux. Prove SVC interception, registers, errno, signals, TLS, 4/16 KiB page behavior, and teardown.
  2. Week 2 — real loader boundary. Map a real pinned shared-cache image; complete chained and authenticated fixups; call through an ARM64e target without modifying the source artifact.
  3. Week 3 — Mach state. Allocate and transfer port rights, perform request/reply and timeout, then make one real bootstrap/XPC lookup through a Darlingserver-derived state owner.
  4. Week 4 — first real service. Start one actual Simulator-domain daemon and advance to a named readiness message. Measure missing operations; do not guess the rest of the dependency graph.

Parallel build gate. During the same month, build one existing, unmodified SwiftPM iOS repository on Linux into a Simulator .app. Inventory every failure as compiler, SDK/module, host tool, resource compiler, build graph, or script behavior. This is a separate feasibility track from runtime boot.

Continue only if all five gates work. Failure in native ARM64e execution, shared-cache layout, the Mach state model, or an unmodified Linux build changes the architecture. Failure in one service contract changes the worklist, not the layer.

Economics

session cost = host hourly cost ÷ useful concurrent sessions + storage + network

At $1/hour, $0.03 per session-hour requires at least 34 productive sessions before storage and network. The real target should therefore be 50–100 warm sessions per host, leaving room for idle capacity and overhead.

That favors native ARM64 execution, shared immutable dyld/runtime pages, per-session COW data, headless pixels, no per-session compositor window, and aggressive suspension of idle sessions. A full VM can share disk blocks but generally pays more private kernel and daemon memory per session.

Layer notes

Source-compatible replacement SDK/runtime

Compile the repository without changing its source, but provide replacement SDK modules and runtime frameworks. touchHLE proves this can produce graphics, touch, and audio, but deliberately targets early 32-bit games and says UIKit remains incomplete.[6] Modern SwiftUI moves enormous behavior into a private, versioned framework graph. The user contract stays clean; the compatibility tail does not.

Headless CoreSimulator

Run real Simulator-targeted ARM64 code and real Simulator runtime frameworks, but implement only the Darwin and host contracts actually reached. This is not “port CoreSimulator” as one library; it is a narrow operating-system personality plus a service graph. The pinned target also contains ARM64e images, so matching the base ISA does not remove PAC, dyld, Mach IPC, TLS, identity, or graphics work.[1]

Full Darling-like personality

Generalize the compatibility layer until broad macOS software runs. Architecturally useful, but AppKit, desktop session services, packaging, and unrelated frameworks consume time without improving a headless iOS agent session.

XNU/macOS micro-VM

Keep real kernel semantics and run CoreSimulator above a virtual macOS host. This trades syscall/Mach reimplementation for boot-chain, kernel, virtual-device, filesystem, GPU, and host-service work. It becomes attractive only if the userspace personality repeatedly fails on irreducible kernel semantics.

Full iOS VM

Boot XNU and device iOS. The public QEMU project reached launchd, binaries, SSH, disks, and a textual framebuffer on iOS 12.1—not a modern graphical app loop.[7] Rendering, touch, audio, microphone, GPU behavior, restore, and modern hardware models remain the expensive path.

Corellium-like virtualization

Run iOS against modeled Apple hardware below XNU. Corellium documents Arm-on-Arm type-1 virtualization, EL2 isolation, device trees, and virtual MMIO.[C1][C6] This is the right layer for device and kernel research, but coding agents mostly need app/runtime behavior.
