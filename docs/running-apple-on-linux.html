Running Apple on Linux

Corellium, reconstructed from its own documentation, code, and engineering notes.

Hover a citation to read its evidence. Open it for the exact excerpt and full offline source.

The answer

iOS is not running as a Linux program. Corellium runs an Arm virtual machine under its CHARM type-1 hypervisor on an Arm server.[1] The virtual device is isolated at Arm’s EL2 hypervisor level.[3]

Corellium’s appliance environment is Ubuntu-based,[4] but the public material does not say that Linux executes or translates iOS system calls. A better mental model is iOS under CHARM, with Linux around the appliance and control layer—not iOS layered on top of Linux.

The system in one picture

What they built

A software model of a device—not merely an app runtime.

The guest sees virtual CPU cores, memory, storage, buses, and peripherals arranged like the target machine. The operating system receives a device tree describing that hardware.[5]

What does “model” mean?

When guest code reads or writes a hardware address, software must reproduce the device’s expected behavior. Corellium explicitly exposes virtual memory-mapped I/O for this purpose.[6]

How broad is that idea?

Its public CoreModel API can attach peripheral models to UART, I²C, SPI, CAN, GPIO, and USB Host buses.[7] This is direct evidence of the mechanism, although it does not expose Corellium’s private iPhone models.

A controllable research machine.

Corellium can build root access into virtual iOS because it controls the software stack, rather than waiting for a vulnerability-based jailbreak.[8]

An observation and replay system.

CoreTrace records system calls with timestamps captured by the hypervisor.[9] CoreXight can combine whole-VM code-flow and system-call traces.[10] Snapshots save storage and, for live snapshots, RAM.[11]

Why it exists

Why not use Apple’s Simulator?

The research target is often the OS, kernel, boot process, or hardware interaction—not only an app API. Corellium runs Arm code on Arm hardware and models the surrounding device.[1]

Why does native Arm matter?

The main instruction stream need not be translated to an unrelated host architecture. That improves fidelity and leaves the hypervisor to virtualize privileged execution and devices.

Why not use a physical iPhone?

A virtual device can expose root access, whole-machine tracing, exact saved states, cloning, and rapid rollback. These properties turn a difficult-to-observe phone into a controlled experiment.[8][10][11]

Why is rollback especially important?

Fuzzing repeatedly mutates one input from the same starting point. MicroSnapshots record changes, run a short test, and roll back without rebuilding the machine.[12]

How it works

  1. Choose a device and firmware. The controller stores firmware and uploaded boot artifacts, then schedules the virtual device onto a compute node.[2]
  2. Create the machine boundary. CHARM runs on the Arm server as a type-1 hypervisor; Corellium places virtual devices at EL2 and assigns CPU cores.[1][3]
  3. Present Apple-shaped hardware. A device tree tells iBoot and XNU which devices and buses exist; device models answer the guest’s MMIO and bus activity.[5][6]
  4. Boot the guest software. iOS follows its own user-space → XNU → hardware-facing path, but the “hardware” at the bottom is the virtual model.
  5. Observe at the boundary. Because the hypervisor sits below the guest, it can expose traces and state that an ordinary in-guest debugger cannot easily provide.[9][10]
  6. Save the experiment. Disk and RAM state can be captured, restored, cloned, or rewound for another run.[11][12]
Where does the “hardware” code live?

Corellium publishes an SDK for building virtual models and says it is the same tool its engineers use internally.[13] Public VMMIO and CoreModel interfaces show two extension paths: memory-address handlers and bus-attached peripheral processes.[6][7]

How they approached the engineering

Important boundary: Corellium has not published a history of CHARM’s implementation. Project Sandcastle is its clearest primary-source account of using its virtual hardware to understand and bring up an unfamiliar Apple machine.

The loop: model → boot → observe → correct

Corellium says its software device model plus knowledge of Android and iPhone hardware enabled rapid iteration.[14]

  1. Start with the SoC model and kernel loader.
  2. Make output work first. Their first driver was the UART, so failures became visible.
  3. Bring up foundational buses and interrupts. They implemented SPI, I²C, the interrupt controller, and an unusual timer path.
  4. Reach a tiny shell. A ramdisk prompt proved CPU, memory, exceptions, timer, console, and enough boot plumbing worked.
  5. Add complex hardware. Multi-core startup, PCIe, NVMe storage, touch, and Wi-Fi followed.
  6. Compare with physical hardware. Mismatches became corrections to the model or driver.

The fast debugger, logging, patching, and reboot cycle were central to kernel bring-up.[15] They developed much of the PCIe driver in the VM, then verified low-level register behavior on a physical phone.[16]

Why this process is illuminating

A device model is an executable hypothesis about hardware. If the real OS boots and its drivers behave correctly, the hypothesis is increasingly accurate. A mismatch—wrong page size, one-shot boot register, unexpected DMA behavior—reveals what the model omitted.

What the evidence does—and does not—establish

Directly documented
Arm-on-Arm virtualization; CHARM as a type-1 hypervisor; EL2 isolation; controller and compute roles; device trees; VMMIO and bus models; hypervisor tracing; snapshots.
Strong architectural inference
Guest hardware accesses must be handled by CHARM or associated device models, and the selected Apple boot artifacts must be made compatible with that modeled machine.
Not disclosed in this corpus
CHARM source code; the complete iPhone device model; exact VM-exit paths; precise changes to each iOS boot chain; and the fidelity or implementation of every subsystem such as SEP, baseband, and GPU.
