[1] Pinned target inventory

Local source: ios-simulator/plan_to_make_port.md, lines 37–41 · captured in the local project

“The real Simulator executable is ARM64. CoreSimulator and SimulatorKit include ARM64e images. Matching the host ISA avoids general CPU emulation but does not remove Mach-O, dyld, PAC, TLS, VM, Darwin syscall, Mach IPC, service, or graphics translation.”

“Kakehashi demonstrates native Darwin ARM64 execution on Linux AArch64 across a carefully managed syscall/TLS boundary but does not implement Mach or GUI application behavior. Darling demonstrates a Mach-O loader, userspace kernel server, Mach IPC, syscall translation, and partial framework/service replacements. … None runs this target.”

[6] touchHLE

Snapshot: touchHLE/touchHLE at 331903de883405a8597036e4ed5ce8333f1604c9

Local source: compatibility-lab/implementations/touchhle/README.md

“Instead of running iPhone OS inside emulation, touchHLE itself takes the place of iPhone OS and provides its own implementations of the system frameworks (Foundation, UIKit, OpenGL ES, OpenAL, etc).”

Its stated targets are iPhone OS 2.x and 3.0; its roadmap says “Never: 64-bit iOS.” It also says “UIKit is easily the most hacky and incomplete of the large frameworks that have been implemented.”

[8] xtool

Snapshot: xtool-org/xtool at 2d58d987edff728fccebc6df643b1672e3583f00

Local source: compatibility-lab/implementations/xtool/README.md

“Cross-platform Xcode replacement. Build and deploy iOS apps with SwiftPM on Linux, Windows, and macOS.”

Its overview claims: “Build a SwiftPM package into an iOS app,” “Sign and install iOS apps,” and interaction with Apple developer services.

This demonstrates a Linux iOS build path for SwiftPM-shaped projects. It does not establish arbitrary .xcodeproj/.xcworkspace, every Xcode build phase, or Simulator runtime execution.
