Apple Process Architecture

Read one line. Open only when you want the next layer.

The short version

  1. You open an app. macOS creates a process.
  2. The kernel maps its Mach-O; dyld connects its libraries.
  3. If it needs a helper, XPC may cause launchd and xpcproxy to start one.

Your OS course, translated

  • Process management → launchd supervises; xpcproxy launches; exec replaces
  • Executable loading → Mach-O, dyld, dylibs
  • IPC → XPC over Mach messages
  • Threads and scheduling → still handled by the kernel
  • Protection → code signing, entitlements, sandbox
  • Protected keys and biometric policy → Secure Enclave

Kernel and scheduler

kernel — The privileged core of the operating system.

It controls hardware access and enforces boundaries between processes. macOS uses the XNU kernel, which combines Mach, BSD, and Apple driver infrastructure.13

Then what is a GPU kernel?

A GPU kernel is a small compute function run many times over data. It is code managed by the OS and GPU stack—not the privileged core of the OS.15

scheduler — Chooses which runnable thread uses a CPU core next.

It considers readiness, priority, quality of service, and time. The scheduler runs inside the kernel and schedules threads, not abstract “apps.”14

Why threads rather than processes?

A thread is the object that has a program counter and actually executes instructions. A process can contain many threads.

Secure Enclave

SEP / Secure Enclave — A security subsystem separate from the main processor.

It is integrated into the Apple system-on-chip but isolated from the Application Processor. Its purpose is to protect sensitive data even if the main processor’s kernel is compromised.26

Is it another macOS process?

No. XNU and macOS run on the Application Processor. The Secure Enclave has its own processor, protected memory, secure boot chain, and operating system.

Where it sits
Why does the Secure Enclave exist?

Some secrets need a stronger boundary than an ordinary process or the main kernel.

Why is a process boundary insufficient?

A compromised kernel controls ordinary process memory.

Why use a separate processor?

It can execute security policy without sharing the main processor’s execution core or trust boundary.

Why request an operation instead of reading the key?

The caller can receive a signature or approval while the protected key remains inside the enclave.

Why is this not absolute protection?

The Secure Enclave reduces what a main-system compromise exposes; it does not make hardware, software, or surrounding protocols infallible.

CoreSimulator and Simulator.app

CoreSimulator is the machinery. Simulator.app is the window.

CoreSimulator — Xcode’s simulated-device backend.

It manages device definitions, runtime versions, device data, boot and shutdown, app installation and launch, and device I/O. “CoreSimulator” names a stack of frameworks, services, helpers, and runtime processes—not one virtual iPhone process.27

Does it boot a complete iPhone?

No. Unlike Corellium’s full virtual hardware, Apple’s Simulator does not boot a separate iPhone XNU kernel or model the complete iPhone SoC. Simulator-targeted iOS user-space processes run over the host macOS kernel.

Simulator.app — The macOS graphical client.

It draws the device window, presents the display, maps Mac input to simulated touch and buttons, and provides menus. Its executable links to CoreSimulator, SimulatorKit, and AppKit.28

Is it required to run an app?

No. Apple’s simctl command can boot a device, install and launch an app, terminate it, and capture screenshots without using Simulator.app’s window.27

simctl — A command-line client for CoreSimulator.

It requests operations from the same simulator backend without providing a device window.27

Why does this matter for coding agents?

An agent needs lifecycle, pixels, input, logs, and files. It does not need the human-facing macOS application around them.

How the pieces relate
Will CoreSimulator run an iOS app?

Yes, when the app is built for the iOS Simulator. Xcode or the Swift compiler produces a simulator-targeted .app; CoreSimulator installs and launches it. CoreSimulator does not compile the source itself.27, 29

Will it run an arbitrary .ipa built for an iPhone?

Usually no. A device app and a Simulator app are different build platforms. Apple records them with different platform IDs and target environments. On Apple Silicon both may contain ARM64 instructions, but their platform metadata, linked system libraries, signing context, and hardware assumptions differ.29

What if I have the Swift source?

Build the source for the iphonesimulator target. That is the normal path for agent-driven development and testing.

Does it reproduce every behavior of a physical iPhone?

No. App UI, lifecycle, files, networking, and much framework behavior can run. Device-only hardware and security behavior—such as SEP, baseband, some sensors, and exact GPU or timing behavior—requires a physical or full-system device environment.

For the Linux project: the valuable target is the CoreSimulator backend and simulator runtime. Reproducing Simulator.app’s macOS window is optional.

Kernel, OS, and CPU names

XNU — The kernel inside macOS.

It occupies roughly the same architectural layer that the Linux kernel occupies inside Ubuntu. Its name expands to “X is Not Unix.” XNU combines Mach, BSD-derived Unix facilities, and I/O Kit driver infrastructure.13, 16

More precise

XNU is not macOS. macOS also includes system services, frameworks, command-line tools, and the graphical environment.

Linux / Ubuntu — A kernel / an operating-system distribution.

Linux manages hardware and processes. Ubuntu packages Linux with user-space tools, services, software management, and a usable system.17, 18

More precise

Calling Ubuntu “Linux” is common shorthand, but Linux itself is the kernel.

BSD Unix — A Unix lineage originating at Berkeley.

Modern BSD systems descend from that lineage. Inside XNU, the BSD subsystem supplies familiar Unix concepts including processes, users, permissions, files, sockets, and much networking behavior.13, 19

More precise

macOS is not simply FreeBSD with a GUI. XNU integrates BSD-derived facilities with Mach and Apple-specific components.

ISA — The instruction-set contract between software and a CPU.

It defines machine instructions, registers, and fundamental execution behavior. ARM64 and x86-64 are different ISAs.

More precise

An operating system and its apps must contain code built for an ISA the CPU can execute, or use translation.

ARM64 — The 64-bit Arm instruction set used by Apple Silicon.

Arm calls the execution state AArch64; Apple tools commonly say arm64. M-series Macs execute this instruction set natively.20

More precise

ARM64 describes instructions, not the whole chip. Apple Silicon also contains GPUs, media engines, memory controllers, and other hardware.

Intel / x86-64 — A chip vendor / the ISA used by Intel Macs.

Intel made the CPUs in older Intel Macs; their 64-bit Mac software uses the x86-64 instruction set.20

More precise

“Intel” names the vendor. x86_64 names the architecture; AMD64 is another name for essentially the same 64-bit ISA family.

universal binary / Rosetta 2 — Two compatibility strategies.

A universal Mach-O contains arm64 and x86-64 slices. On Apple-silicon Macs, Rosetta translates x86-64 code when no arm64 slice is available.20, 21

Is Rosetta included with every macOS?

No. It is irrelevant on Intel Macs. Before macOS 27, an Apple-silicon Mac may offer to install it when an Intel app first needs it. macOS 27 integrates translation; macOS 28 limits Rosetta to certain older games.25

A concrete example

You open a Mac app that uses a thumbnail helper
  1. macOS finds the app bundle and its executable.
  2. The kernel creates a process and maps the Mach-O.
  3. dyld loads the frameworks the app needs.
  4. The app begins running. Its threads are scheduled normally.
  5. The app sends “make this thumbnail” over XPC.
  6. If the helper is not running, launchd starts it through xpcproxy.
  7. The helper replies over XPC. The app displays the thumbnail.

Why ladders

Each answer opens the next question.

launchd: Why does it exist?

To start and supervise services.1

Why centralize that?

So activation, restart, identity, and policy follow one system model.

Why activate services on demand?

So every service need not run from boot or stay resident.

Why address a service by name instead of PID?

A name survives when a process exits or restarts.

Why must that survive?

Clients need the service, not one fragile process instance.

xpcproxy: Why does it exist?

To configure an XPC service’s execution environment inside the new service process before its code runs.2

Why prepare the environment first?

The service must begin with the intended identity, resources, and launch context.

Why not let the service prepare itself?

Security-sensitive setup must already be true when service code begins.

Why use exec afterward?

It replaces the setup program with the target while preserving allowed process state.

Why a system-owned transition program?

Likely to centralize trusted setup. Apple documents the behavior, not this design rationale.

trampoline: Why does this programming term exist?

It names short-lived code that receives control and immediately redirects it.

Why not call the destination directly?

The transition may need setup, adaptation, or indirection first.

Why is it short-lived?

It performs the handoff, not the destination’s ongoing work.

What is being “jumped over”?

Nothing specific. The metaphor only suggests landing briefly and continuing elsewhere.

How does this apply to xpcproxy?

Control enters xpcproxy, setup happens, and exec replaces it with the service.

exec: Why replace a process image?

So a prepared process can hand control to a different program.

Why reuse the process container?

Selected descriptors, ports, credentials, and the PID can carry into the target.

Why separate preparation from execution?

Unix composes “create context” and “choose program” as separate operations.

Why is that useful to macOS?

The OS can establish launch conditions before third-party code runs.

Why does this matter for xpcproxy?

The temporary setup program disappears; the prepared process becomes the service.

dyld: Why does it exist?

To connect an executable to dynamic libraries at launch.3

Why use dynamic libraries?

Many programs can reuse system code instead of embedding private copies.

Why defer some linking until launch?

Only then are the chosen library images and runtime locations known.

Why are runtime locations not fixed?

ASLR and shared-cache layout place images at actual runtime addresses.

Why vary addresses?

Randomization impedes predictable attacks; cache layout reduces repeated launch work.

kernel: Why does it exist?

To provide one privileged authority over hardware and process boundaries.13

Why must anything be privileged?

Apps must not directly rewrite memory mappings, control devices, or inspect other processes.

Why mediate those operations?

Many untrusted programs must safely share one machine.

Why is there a user/kernel boundary?

Crossing through controlled system calls lets the kernel validate requests and enforce policy.

Why is XNU more than one subsystem?

macOS combines Mach mechanisms, BSD Unix semantics, and driver infrastructure behind that boundary.

scheduler: Why does it exist?

Runnable threads usually outnumber available CPU cores.14

Why schedule threads rather than apps?

Threads are the units that hold execution state and run instructions.

Why interrupt and switch between them?

One compute-heavy thread must not monopolize a core.

Why use priority and quality of service?

Interactive, audio, and background work have different latency needs.

Why must the scheduler be in the kernel?

Only the kernel can safely stop a thread, save its state, and assign the core to another.

GPU kernel: Why is it called a kernel?

It is the small core computation dispatched repeatedly over data.15

Why run many copies?

Graphics and numerical workloads often apply the same operation to many pixels or elements.

Why use a GPU?

Its many execution units favor parallel throughput.

Why is this not an OS kernel?

It is ordinary workload code, not the privileged manager of the machine.

What do the meanings share?

Only the idea of a central or essential core; their responsibilities are unrelated.

XNU: Why does it have its own name?

“X is Not Unix” identifies Apple’s kernel project, not the complete macOS product.16

Why is a kernel only one part of macOS?

A usable OS also needs services, libraries, tools, application frameworks, and a user interface.

Why does XNU combine Mach and BSD?

Mach supplies low-level tasks, threads, memory, and IPC; BSD supplies the familiar Unix process, file, socket, and user model.

Why include I/O Kit too?

The kernel also needs a structured way to drive hardware devices.

Why compare XNU with Linux?

Both occupy the kernel layer; comparing XNU with Ubuntu mixes a component with a complete OS.

Linux / Ubuntu: Why are they different names?

Linux is a kernel; Ubuntu is a complete distribution built around it.17, 18

Why is the kernel not enough?

Users also need startup services, shells, libraries, package management, applications, and often a desktop.

Why package those as a distribution?

The pieces must be selected, integrated, updated, and supported together.

Why are there many Linux distributions?

They choose different defaults, release policies, interfaces, and target uses.

What is the clean comparison?

XNU ↔ Linux at the kernel layer; macOS ↔ Ubuntu at the complete-system layer.

BSD Unix: Why is it inside XNU?

macOS needs mature Unix process, file, user, socket, and networking semantics.13, 19

Why does Mach not provide all of that?

Mach focuses on lower-level tasks, threads, virtual memory, and message-based IPC.

Why keep the BSD model visible?

It supplies the Unix APIs and behavior expected by shells, servers, and portable software.

Why integrate BSD with Mach?

macOS needs both the Unix programming model and Mach’s kernel mechanisms.

Why is macOS not simply “BSD”?

BSD is one major lineage and subsystem within a larger Apple system.

ISA: Why does it exist?

Software and a CPU need an exact agreement about machine instructions and registers.

Why are there multiple ISAs?

Processor families evolved with different encodings, capabilities, and design tradeoffs.

Why must code target one?

ARM64 bytes do not mean the same instructions to an x86-64 processor.

Why must the kernel target it too?

The kernel performs context switches, handles exceptions, and controls hardware using that CPU’s rules.

Why do universal binaries or translation exist?

They bridge software distribution across incompatible instruction sets.

ARM64: Why does it matter on a Mac?

It is the native instruction set executed by Apple Silicon CPUs.20

Why “64”?

The architecture uses 64-bit general-purpose registers and a 64-bit execution model.

Why is it also called AArch64?

AArch64 is Arm’s name for the 64-bit execution state; arm64 is Apple’s common toolchain name.

Why is ARM64 not the same as Apple Silicon?

ARM64 is an instruction set; Apple Silicon is a family of whole chips implementing it.

Why does software care?

A Mach-O executable needs an arm64 slice to run natively on that CPU.

Intel / x86-64: Why are both names used?

Intel names the vendor used in older Macs; x86-64 names the instruction set their Mac software uses.20

Why say “Intel app”?

It is convenient shorthand for a Mac executable containing x86-64 code.

Why can’t ARM64 execute it directly?

The instruction encodings and CPU execution model are different.

Why does the app still work through Rosetta?

On a supported Apple-silicon Mac, Rosetta translates x86-64 instructions into executable arm64 code.21, 25

Why prefer an arm64 build?

Native code avoids translation and can target the current platform directly.

Apple Silicon: Why is it more than an ARM64 CPU?

It is a system on a chip containing CPU cores plus GPU, memory, media, security, and other engines.

Why integrate those parts?

They can share packaging, memory architecture, and system-level design decisions.

Why does the OS need to know the platform?

The kernel and drivers must manage those concrete processors and devices.

Why does an app usually care less?

Frameworks and the OS abstract most hardware details behind stable APIs.

When does an app care directly?

When choosing binary slices, using specialized accelerators, or optimizing architecture-specific code.

universal binary / Rosetta 2: Why do both exist?

They solve compatibility differently during the Intel-to-Apple-Silicon transition.20, 21

Why put two slices in one universal binary?

Each Mac can select native code while users download one app.

Why use Rosetta when no arm64 slice exists?

Translation preserves access to older x86-64 software.

Why is translation not identical to native execution?

Instructions must be converted and some architecture-specific assumptions may not carry over.

Why is this below most app logic?

The OS, loader, and Rosetta handle the architecture boundary before ordinary app behavior.

process / PID: Why have processes?

To give running programs separate execution and memory containers.

Why separate them?

Faults and authority can be contained instead of spreading through one address space.

Why assign a PID?

The kernel and tools need a handle for one live instance.

Why is a PID temporary?

Processes end, and the finite identifier space is reused.

Why use a service name too?

A logical service must remain findable across PID changes and restarts.

XPC: Why does it exist?

To turn low-level IPC into structured connections to services.4, 6

Does XPC replace Mach ports?

No. XPC uses Mach messages underneath; Mach supplies the protected transport.

Then what does XPC add?

Object encoding, asynchronous handlers, connection errors, peer identity, and service lifecycle integration.

Why not use raw Mach messages?

The application would have to define and correctly implement those pieces itself.

Why keep Mach underneath?

The kernel still needs a small, general mechanism for enforcing rights, queueing messages, and crossing process boundaries.

Why structured, asynchronous messages?

They reduce protocol mistakes and avoid making one process wait synchronously by default.

Why include connection lifecycle events?

The remote process can start, stop, crash, or be replaced.

Why expose peer identity?

An IPC boundary is also an authorization boundary.

XPC service: Why does it exist?

To move work behind a separate process boundary.5

Why use a separate process?

A crash or compromise can be contained away from the main app.

Why does a process boundary help?

Memory and privileges are separate; the kernel mediates crossings.

Why make crossings explicit?

The interface can expose only the operations the helper should perform.

Why is narrower authority valuable?

It reduces the blast radius of malformed input, bugs, and compromise.

Mach / Mach port: Why do they exist?

Separate processes need kernel-mediated communication endpoints.6

Why communicate through ports?

A port gives messages a destination and a kernel-managed queue.

Why use port rights?

Possession determines who may send, receive, or transfer access.

Why are port names local to each task?

A plain integer in one process should not grant authority in another.

Why is that important?

The reference acts like a capability, not a globally forgeable address.

Why is a Mach port not already an XPC service?

A port is an endpoint and rights. It does not define request objects, handler methods, service activation, or connection lifecycle.

Mach-O / load command: Why do they exist?

The kernel and dyld need a contract describing native code.7

Why does it share the name “Mach”?

Mach-O means Mach object file format. It was created for Mach-based systems; it is not the Mach kernel or Mach IPC.

Why put mapping instructions in the file?

The loader must know which bytes become code, data, dependencies, and signatures.

Why use separate load commands?

The format can add new metadata without redesigning executable instructions.

Why separate metadata from code?

Tools can inspect and validate the program without running it.

dylib / framework: Why do they exist?

To package reusable code instead of copying it into every app.8

Why load shared code dynamically?

Programs can share read-only pages and depend on system-provided implementations.

Why also have frameworks?

Code often needs resources, metadata, headers, and version structure.

Why record install names and run paths?

dyld needs rules for locating dependencies after an app is moved.

Why resolve that at runtime?

The final bundle location and compatible library set are runtime facts.

dyld shared cache: Why does it exist?

Most processes load many of the same system libraries.

Why prepare them together?

The OS can perform layout and linking work once instead of per launch.

Why does that improve memory use?

Processes can map the same prepared, read-only pages.

Why does it improve launch time?

Less discovery, mapping, and fixup work is repeated.

Why can Apple optimize it globally?

The OS controls the system-library set and rebuilds the cache as a unit.

code signing: Why does it exist?

To bind executable code to identity and integrity information.9

Why must code have identity?

Security decisions need to refer to something stronger than a filename or path.

Why seal the code’s contents?

Identity should stop applying if protected code is modified.

Why enforce this outside the app?

A program cannot be trusted to validate itself before it runs.

Why is signing foundational?

Entitlements and other policies must remain attached to the exact approved code.

entitlement: Why does it exist?

To express a narrow capability as signed metadata.10

Why must it be signed?

An app must not be able to grant itself new authority by editing a file.

Why use narrow capabilities?

Most apps need only a small subset of system powers.

Why deny the rest by default?

Unused authority becomes unnecessary attack surface.

Why does least privilege matter?

A compromised component can abuse only the capabilities it actually received.

App Sandbox: Why does it exist?

To restrict an app below the full authority of the signed-in user.11

Why is the user account not enough?

A normal user can access far more data than one app should need.

Why enforce policy in the OS?

The kernel can mediate file, network, IPC, and other resource access.

Why allow entitlements and temporary extensions?

Apps still need explicit, controlled routes to legitimate resources.

Why sandbox an XPC service separately?

Each compartment can receive only the authority required for its one job.

bundle / Info.plist: Why do they exist?

To package an app and describe it without running it.12

Why package code and resources together?

The system and user can move and manage one coherent app.

Why use declarative metadata?

macOS can discover the executable, document types, and services safely and cheaply.

Why not ask the app itself?

Launching unknown code merely to identify it would be slow and unsafe.

Why include the bundle in signing?

Code, metadata, and protected resources must remain one trusted unit.

Terms

launchd — The long-lived service supervisor.

It activates jobs on demand, creates their processes, and continues managing their lifecycle.1

More precise

It decides what should run; it does not link libraries.

xpcproxy — A temporary setup program.

Inside the new child process, it configures the environment, then exec replaces it with the service.2

More precise

Apple calls it an “exec trampoline”: control enters briefly, setup happens, then control transfers to the service.

trampoline — Short-lived transition code.

Control lands there briefly, it may perform setup, then it transfers control elsewhere.

More precise

Nothing specific is jumped over. It is only a metaphor for an immediate handoff.

exec — Replaces the program inside a process.

The new executable runs in the same process container.2, 6

More precise

The PID normally stays the same; the process image changes.

dyld — Makes a dynamic program runnable.

It maps libraries, fixes addresses, and runs initializers before ordinary program code.3, 7

More precise

It links at launch; it does not decide whether to launch.

kernel — The privileged core of the operating system.

It controls hardware access and enforces boundaries between processes. macOS uses XNU.13

More precise

Most app code runs in user space and enters the kernel through controlled operations such as system calls.

scheduler — Decides which runnable thread uses a CPU core next.

It runs inside the kernel and considers readiness, priority, quality of service, and time.14

More precise

It schedules threads; a process is their resource and address-space container.

SEP / Secure Enclave — Apple’s isolated security subsystem.

It performs protected operations and enforces security policy outside the main macOS kernel’s trust boundary.26

More precise

SEP commonly means Secure Enclave Processor. Apple uses “Secure Enclave” for the complete subsystem; the processor is one component inside it.

CoreSimulator — Xcode’s simulated-device backend.

It manages simulator devices, runtimes, lifecycle, app installation, launch, and I/O.27

More precise

It is a collection of frameworks, services, helpers, and runtime processes—not Simulator.app and not one process.

Simulator.app — The graphical Simulator client.

It presents the simulated display and turns Mac input into device input.28

More precise

Closing the conceptual window does not remove the CoreSimulator backend; command-line clients can operate it directly.

simctl — Apple’s Simulator control command.

It boots and controls devices and can install, launch, terminate, and inspect apps without Simulator.app.27

.app / .ipa — An app bundle / a packaged device-app archive.

CoreSimulator normally installs a .app built for the Simulator platform. An iPhone-device .ipa is not automatically Simulator-compatible.29

GPU kernel — A compute function run many times on a GPU.

It is application workload code, not the privileged OS kernel.15

More precise

The shared word “kernel” means a central computation or core; the two roles are otherwise different.

XNU — The kernel used by macOS.

Its name means “X is Not Unix.” It integrates Mach, BSD-derived Unix facilities, and I/O Kit driver infrastructure.13, 16

More precise

XNU relates to Linux; macOS relates to Ubuntu.

Linux / Ubuntu — A kernel / a complete OS distribution.

Ubuntu combines the Linux kernel with user-space software, services, package management, and system defaults.17, 18

More precise

“Linux” commonly names whole systems in conversation, but technically identifies the kernel.

BSD Unix — The Berkeley branch of the Unix family.

XNU’s BSD subsystem supplies much of macOS’s Unix process, file, user, socket, and networking model.13, 19

More precise

BSD is one integrated part of XNU and macOS, not the entire system.

ISA — The machine-language contract understood by a CPU.

It defines instructions, registers, and basic execution behavior. ARM64 and x86-64 are different ISAs.

More precise

Source code can be portable; the compiled machine code must target a compatible ISA.

ARM64 / AArch64 — The 64-bit Arm instruction set.

Apple Silicon Macs execute arm64 code natively.20

More precise

ARM64 is an ISA; Apple Silicon is a family of whole chips implementing it.

Intel / x86-64 — A chip vendor / its Macs’ instruction set.

Older Intel Macs execute x86-64 Mac code natively.20

More precise

“Intel app” is shorthand for a Mac app containing x86-64 code.

Apple Silicon — Apple’s Arm-based system-on-chip family.

It combines arm64 CPU cores with GPU, media, memory, security, and other hardware engines.

More precise

M1, M2, M3, M4, and related chips are Apple Silicon; ARM64 is the instruction set their CPUs implement.

universal binary / Rosetta 2 — Native slices / instruction translation.

A universal Mach-O can contain arm64 and x86-64 code. Rosetta translates x86-64 code on Apple Silicon.20, 21

Availability

Apple-silicon Macs only. Before macOS 27: install when needed. macOS 27: integrated. From macOS 28: limited to certain older games.25

process / PID — A running program / its temporary number.

A process owns memory and execution state. Its PID identifies that instance.6

More precise

An app can use several processes; a PID is not permanent identity.

XPC — Apple’s structured process-messaging system.

It provides asynchronous connections, typed messages, and service lifecycle integration.4, 5

More precise

XPC uses Mach messages as transport, then adds object encoding, handlers, errors, identity, and lifecycle. xpcproxy is separate launch machinery.

XPC service — A separate program that receives XPC work.

It is commonly bundled inside an app and launched when needed.1, 5

More precise

Its separate process creates a reliability and security boundary.

Mach / Mach port — Low-level IPC / a message endpoint.

XPC relies on lower-level mechanisms including Mach messages and port rights.6

More precise

A Mach port is not a network port or a service framework. It is a kernel-managed message endpoint; a port right conveys authority.

Mach-O / load command — Native binary / loader metadata.

Load commands describe memory segments, dependencies, signatures, and entry information.7

More precise

A load command is metadata, not a shell or CPU instruction.

dylib / framework — Shared code / a bundle that may contain it.

dyld connects an executable to the libraries and frameworks it needs.3, 8

More precise

A dylib is a binary; a framework is a package.

dyld shared cache — Optimized system-library collection.

The OS maps prepared system-library data to reduce repeated launch work.3

More precise

It is an OS detail, not an app document cache.

code signing — Establishes identity and detects changes.

The OS verifies the signature and evaluates code under platform policy.9

More precise

A valid signature does not mean the program is bug-free.

entitlement — A signed security-capability declaration.

The OS evaluates entitlements when code requests protected features.10

More precise

It is security metadata, not an ordinary Info.plist setting.

App Sandbox — Limits resources a process may access.

It can restrict a process even when the user has broader access.11

More precise

Sandboxing limits access; signing establishes code identity.

bundle / Info.plist — App package / its metadata.

A bundle contains executables and resources; Info.plist describes them to the system.12

More precise

The bundle contains the executable; it is not the executable.

Appendix — Names and abbreviations

XNU — “X is Not Unix.”

Apple’s source repository gives that exact self-referential expansion. XNU contains Unix facilities, but the kernel is a hybrid rather than one original Unix kernel.16

BSD — Berkeley Software Distribution.

A branch of Unix developed at the University of California, Berkeley. XNU incorporates BSD-derived components.19

ARM — A historical acronym; today, “Arm” is the name.

It began as “Acorn RISC Machine” and later became “Advanced RISC Machines.” Modern Arm uses the word as its company and architecture brand.22

RISC — Reduced Instruction Set Computer.

A processor-design tradition emphasizing regular, efficient instructions. The name is historical and comparative; modern Arm CPUs are still highly sophisticated.23

AArch64 / arm64 — Arm Architecture 64-bit / Apple’s architecture label.

AArch64 is Arm’s name for its 64-bit execution state. Apple tools and Mach-O files commonly use arm64.20, 22

x86 / x86-64 — The 8086 family / its 64-bit extension.

The family descends from Intel’s 8086 processor. Later names such as 286, 386, and 486 preserved the “86” lineage.24

ISA — Instruction Set Architecture.

The formal contract describing the machine instructions and registers a processor understands.

IPC — Interprocess Communication.

The general category for communication between processes. XPC, pipes, sockets, and shared memory are IPC mechanisms.

XPC — Apple treats this as a name.

Apple’s public documentation does not give a canonical expansion. “Cross-process communication” describes its purpose, but should not be presented as an official acronym.4

dyld / dylib — Dynamic linker / dynamic library.

These are compact Unix-style names used in commands and filenames.3

launchd — Launch daemon.

The trailing d follows the Unix convention for long-running daemon names.1

Mach-O — Mach object file format.

The native executable and object format used by Apple platforms. The shared name records its Mach lineage; Mach-O is a file format, while Mach is part of the kernel.6, 7

plist — Property list.

Apple’s structured data format for configuration and metadata.

Rosetta — Apple’s instruction-translation system.

Name origin: the Rosetta Stone, which enabled translation between written languages. Rosetta translates program instructions between CPU architectures.

CoreSimulator — Core simulator services.

“Core” distinguishes the backend machinery from the graphical Simulator application.

simctl — Simulator control.

Apple’s command-line utility for requesting CoreSimulator operations.27

IPA — The .ipa device-app archive format.

The archive contains an iOS app bundle and related metadata. The contained executable’s build platform—not merely the filename—determines whether it can run in Simulator.

SEP — Secure Enclave Processor.

The processor supplies the Secure Enclave’s computing power. “Secure Enclave” names the larger subsystem.26
